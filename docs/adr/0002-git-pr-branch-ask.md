# ADR-0002：Git PR 分支要不要用——先问用户

- **日期**：2026-08-21
- **范围**：仓库工作流（不改采集/播放契约）

## 1. 用户提示词

```
在架构决策记录里改一下说以后建议和提醒用户用不用pr分支，git的pr应该是这个意思吧
```

## 2. 背景

本仓库长期在当前分支（多为 `main`）直接改、直接 commit。Git 里的 **PR = Pull Request（拉取请求）**：从主线拉一条功能分支改完，再开合并请求合回去，方便隔离实验、审查、整支丢掉。不是「另一种 commit 格式」。

自用单人仓库不强制走 PR；但以后若功能块变大（例如 `omnitrace_android`），用户可能想用分支。AI 不能默认开分支，也不能默认永远不开。

## 3. 决策

### 决定做

1. **PR 分支 = 可选，默认仍在当前分支改。** 不把「每次必须 PR」写成硬规则。
2. **以后凡非琐碎改动，AI 先提醒/询问一次**：这次要不要开 PR 分支（从当前主线 `checkout -b …`，改完再合）。用户说不用就继续在当前分支；说要用才开分支。用户已经指定分支则不再问。
3. **开了 PR 分支也不等于要推远程、开 GitHub/GitLab 合并页。** 推远程、`gh pr create` 仍须用户另说一声。
4. 琐碎改动（文案、蓝图一句、改错别字）不必每次都问，以免烦。

### 决定不做 / 延后

- 不强制 GitHub Flow / 不强制保护 `main`。
- 不为「提醒用不用 PR」去改采集数据格式或 OmniPlayer。

## 4. 实现要点

- 索引：本文件（`docs/adr/` 仍只是索引，不是唯一真相）。
- 执行提醒：`.cursor/rules/git-commits.mdc`「PR 分支」节（AI 每次会话会读到）。
- 蓝图指针：`.cursor/ARCHITECTURE_BLUEPRINT.md` §6。

## 5. 验证

- [ ] 下一轮非琐碎任务，AI 会问要不要 PR 分支，而不是自己开或自己否。

## 6. 后果与下一刀

- 用户若某次明确「以后默认都开 / 都不要」，再出 ADR 修订默认，不必每轮重复讲定义。
